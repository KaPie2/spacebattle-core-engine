# Журнал архитектурных решений (ADR)

В этом документе фиксируются ключевые технические и архитектурные решения команды, контекст их принятия и последствия.

## ADR-001: Инверсия зависимостей и отказ от `new`
- **Статус:** Принято
- **Контекст:** Жесткая связность через прямое создание объектов ведет к перегрузке Garbage Collector и нарушает принцип OCP.
- **Решение:** Все игровые сущности и команды инстанцируются исключительно через единый `IoC-контейнер` с использованием иерархии `Scopes`.

## ADR-002: Автоматическая генерация адаптеров
- **Статус:** Принято (Реализовано)
- **Контекст:** Ручное написание адаптеров (Boilerplate) под интерфейсы (IMovingObject, IFuelable) неэффективно и нарушает принцип DRY.
- **Решение:** Генератор читает свойства интерфейса через Reflection и подставляет имена типов, свойств и ключи IoC в [TXT-шаблоны](SpaceBattle.Lib/CodeGeneration/Templates). Отдельные шаблоны задают адаптер, фабрику `IAdapterFactory<T>` и команду регистрации. Шаблон свойства содержит секции для геттера и сеттера, которые выбираются по интерфейсу. Основной шаблон можно переопределить через `Adapters.Template` и сохранить сгенерированный исходник адаптера и фабрики в файл. Roslyn компилирует адаптер, фабрику и команду регистрации в одной сборке в памяти. Сгенерированная команда регистрирует фабрику по ключу `Adapters.{Name}`, исходник — по `Adapters.Source.{Name}`, а также стратегии свойств, заданные атрибутами `[Adapter]`.

## ADR-003: Многопоточная изоляция (Actor Pattern и модель N+1)
- **Статус:** Принято. Цикл `GameThread` реализован, схема N+1 проверена нагрузочным тестом.
- **Контекст:** У каждой игры своя очередь команд. Маршрутизатор передаёт команды в очередь нужной игры.
- **Решение:** Один `GameThread` можно использовать как маршрутизатор, а остальные — как игровые потоки. Маршрутизатор обрабатывает общую входную очередь и отправляет команды через `SendCommand`. Каждый игровой поток реализует `ICommandReceiver`, опрашивает свою `BlockingCollection<ICommand>` с тайм-аутом 50 мс и может установить собственный скоуп IoC при старте. Стратегия обработки меняется через `SetStrategy`.

## ADR-004: Обработка исключений в игровом потоке (Chain of Responsibility)
* **Статус:** Принято
* **Контекст:** Выброс исключения внутри атомарной команды не должен приводить к падению всего серверного потока (Actor) или зависанию очереди.
* **Решение:** При создании `GameThread` передаётся функция, которая выбирает команду обработки по исходной команде и исключению. Конструктор проверяет наличие функции до запуска потока. Игровой поток выполняет полученную команду и продолжает работу с очередью. Приложение может связать эту функцию со штатным маршрутизатором `Exception.Handler` в IoC.

## ADR-005: Журнал транзакций для макрокоманд (Commit/Rollback)
* **Статус:** Принято
* **Контекст:** При частичном выполнении макрокоманды (например, топливо списано, но перемещение вызвало ошибку) игровой объект остается в некорректном (сломанном) состоянии.
* **Решение:** Внедрен паттерн Transaction Log. Во время выполнения макрокоманды все изменения записываются во временную структуру. Обновление основного состояния объекта (`UObject`) происходит только после успешного выполнения всей цепочки команд (Commit). При ошибке временные записи отбрасываются (Rollback).

## ADR-006: Изоляция тестов и Mock-объекты
* **Статус:** Принято
* **Контекст:** Модульные тесты IoC-стратегий, макрокоманд и очередей не должны зависеть от сетевых сокетов, баз данных или глобального состояния.
* **Решение:** Для всех внешних зависимостей и изоляции тестовых контекстов строго используются Mock-объекты (Moq/NSubstitute). Каждый тест инициализирует собственный изолированный Scope в IoC-контейнере для предотвращения коллизий ключей.
## ADR-007: Локальный router исключений внутри игрового scope
- **Статус:** Принято
- **Контекст:** Правила обработки исключений должны различаться между игровыми сессиями. Router содержит изменяемую таблицу маршрутов и не должен быть общим глобальным состоянием для всех игр.
- **Решение:** `RegisterIoCDependencyExceptionHandler` создаёт один `ExceptionHandlerRouter` во время настройки конкретного scope. Ссылку на этот router замыкают регистрации `Exception.Handler` и `Exception.Handler.Register`. Сам router не разрешается из глобального контейнера как общий singleton.
- **Обоснование:** Создание router в composition root является созданием инфраструктурного объекта, а не игровой команды. Оно происходит один раз при конфигурации scope, после чего бизнес-код получает router только через IoC-ключи. Это сохраняет изоляцию правил, исключает утечку маршрутов между играми и не требует добавлять идентификатор игры в каждую команду или исключение.
- **Последствие:** Вызов `RegisterIoCDependencyExceptionHandler` должен выполняться для каждого игрового scope. Повторная регистрация заменяет ключи в текущем scope и создаёт новый набор маршрутов.

## ADR-008: Создание повторной команды через IoC
- **Статус:** Принято
- **Контекст:** `RepeatOnceCommand` должна изменить runtime-тип повторяемой команды, но прямое создание `new RepeatedCommand(...)` внутри команды нарушает IoC-first правило проекта.
- **Решение:** В текущем scope регистрируется ключ `Commands.Repeated`. `RepeatOnceCommand` разрешает этот ключ и передаёт ему исходную команду. Фабрика ключа создаёт `RepeatedCommand` в composition root подсистемы обработки исключений.
- **Обоснование:** Команда повторного выполнения зависит от абстракции разрешения, а способ упаковки можно заменить регистрацией. При этом сохраняется важное поведение, когда повторная попытка имеет тип `RepeatedCommand` и не попадает снова в маршрут первого повтора.
- **Последствие:** Перед использованием `RepeatOnceCommand` в игровом scope должна быть выполнена регистрация `RegisterIoCDependencyExceptionHandler` или отдельная регистрация `Commands.Repeated`.

## ADR-008: Переключение игрового скоупа на границе worker
- **Статус:** Принято
- **Решение:** Worker переключает текущий скоуп через системную команду `IoC.Scope.Current.Set`, выполняет команду игры и восстанавливает предыдущий скоуп в `finally`. `GameScopeFactory.Execute` предоставляет эту границу выполнения.
- **Обоснование:** Смена контекста относится к worker-инфраструктуре. Отдельная команда-декоратор для каждой команды игры не требуется.
